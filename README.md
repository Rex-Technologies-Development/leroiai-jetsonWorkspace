# Leroi AI — Jetson ROS 2 Workspace

ROS 2 (`colcon`) workspace for running the Leroi AI stack on NVIDIA Jetson.

This repo is structured as a standard ROS 2 workspace:

- `src/` — source packages
- `build/`, `install/`, `log/` — generated by `colcon` (safe to delete/rebuild)

Main build command (run from the repo root; source the install overlay after building):

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

## Project structure

Each ROS 2 package usually contains:

- one or more node files or node entrypoints
- any supporting Python/C++ code the node needs
- `package.xml` and build/setup metadata

Launch files live in the bringup package, which is used to start one or more nodes together.

## Packages

This workspace contains the following ROS 2 packages:

- `leroi_bringup` — launch package used to start one or more ROS 2 nodes together.
- `leroi_perception` — perception node package for camera input, preview streaming, and YOLO-based detections.
- `leroi_decision` — decision-making package that will consume perception outputs and choose actions.
- `leroi_policy` — policy package for higher-level behavior or control logic that guides decisions.
- `leroi_serial_messenger` — serial communication package for Jetson ↔ microcontroller messaging.
- `leroi_dashboard` — VexAI dashboard sync for robot pose, blocks, and camera stream.
- `leroi_telemetry` — telemetry package for publishing or exporting system status and runtime metrics.
- `leroi_interfaces` — interface package for shared custom messages and services.

Below is a short summary for each package followed by details.

### `leroi_bringup` (ament_python)

Bringup / launch package for the workspace. It contains launch files that start one or more nodes together and pass common parameters.

- Launch files: `perception.launch.py`, `robot.launch.py` (installed via `setup.py` data files)
- What they do: the provided launch files start the `perception_node` from `leroi_perception` and set a small set of default parameters (for example `publish_rate_hz` and `enable_fake_detections`). Edit or add launch files here to compose multiple nodes for your robot.
- Example:

```bash
ros2 launch leroi_bringup perception.launch.py
```

### `leroi_perception` (ament_python)

Full-featured perception package providing `PerceptionNode` (entrypoint `perception_node`). The node supports multiple camera sources (including OAK), an MJPEG preview stream, and an optional YOLO inference pipeline.

- Node entrypoint: `perception_node` (`ros2 run leroi_perception perception_node`) — registered in `setup.py` as `leroi_perception.perception_node:main`.
- Main features:
	- Camera source abstraction via `create_camera_source` (configured by `camera_type`, `camera_index`, `oak_mxid`, and resolution).
	- MJPEG preview streamer (`enable_preview_stream`, `preview_port`, `preview_jpeg_quality`) that serves a live preview (default host 0.0.0.0).
	- Optional YOLO detector wrapper (`YoloDetector`) with parameters to control model path, device, confidence, image size, and half precision.
	- Background camera reader thread plus timers for preview framing, status updates, and YOLO inference.
- Topics (per-camera):
	- `/perception/<camera_name>/status` (`std_msgs/String`) — JSON status packet including timestamps, counts, and runtime stats.
	- `/perception/<camera_name>/detections` (`std_msgs/String`) — JSON detection packet with fields such as `frame_id`, `image_width`, `image_height`, `detection_count`, and `detections` (each detection contains `class_name`, `class_id`, `confidence`, `x,y,z`, and `bbox_*` keys when available).
- Important node parameters (defaults taken from the node implementation):
	- Camera: `camera_name`=`oak_front`, `camera_type`=`oak`, `camera_index`=0, `camera_width`=640, `camera_height`=480, `camera_fps`=30, `oak_mxid`=""
	- Rates: `preview_rate_hz`=30.0, `status_rate_hz`=2.0, `yolo_rate_hz`=15.0
	- YOLO: `enable_yolo`=False, `yolo_model_path`="", `yolo_confidence`=0.35, `yolo_image_size`=320, `yolo_device`="cpu", `yolo_use_half`=False
	- Preview: `enable_preview_stream`=True, `preview_port`=8080, `preview_jpeg_quality`=70, `draw_detections`=True

Examples:

Run via bringup launch (uses defaults set in the launch file):

```bash
ros2 launch leroi_bringup perception.launch.py
```

Run node directly and enable YOLO with a model path:

```bash
ros2 run leroi_perception perception_node --ros-args \
	-p enable_yolo:=true \
	-p yolo_model_path:="/path/to/best.pt" \
	-p yolo_device:=0
```

Notes:
- The node publishes JSON-encoded messages on the status and detections topics to keep interfaces simple while custom messages are developed in `leroi_interfaces`.
- The preview streamer serves frames to `http://<host>:<preview_port>` when enabled.

## Prerequisites

- ROS 2 Humble (this workspace has been built against `/opt/ros/humble`)
- `colcon` + standard ROS 2 build tools
- `pip install 'websockets>=12.0'` for `leroi_dashboard` (do **not** use apt `python3-websockets`; it is too old)

On a machine with ROS 2 installed, you should have access to `colcon` and `ros2` on your PATH after sourcing the ROS setup script.

**Important:** ROS packages must live under `src/` only. Do not copy a package folder (e.g. `leroi_dashboard/`) into the workspace root — `colcon` will fail with "Duplicate package names not supported".

## Device permissions

If the perception stack uses a USB camera or an OAK camera, and if the serial messenger uses a USB serial device, you may need to add your user to the right Linux groups.

Check the device names first:

```bash
ls -l /dev/video*
ls -l /dev/ttyACM*
```

Common permission fixes:

```bash
sudo usermod -aG video $USER
sudo usermod -aG dialout $USER
```

After running those commands, log out and log back in so the group changes take effect.

### Decision command testing

`leroi_bringup/launch/integration_test.launch.py` drives the `decision_node` through a
fixed command sequence so you can verify the action handshake end to end. It brings up
the serial messenger, perception, the decision node, and a `decision_test_driver` that
sends commands one at a time, waiting for each ACK before sending the next:

1. `MOVE_CHASSIS_ONLY` (action_id 1) → first target point
2. `MOVE_CHASSIS_ONLY` (action_id 1) → second target point
3. `COLLECT_BLOCKS` (action_id 2) → several target points

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch leroi_bringup integration_test.launch.py
```

The driver waits 5 s after launch before sending the first command. By default it
expects the **real robot** (via `leroi_serial_messenger`) to return the ACKs on
`/robot/action_ack`; the sequence only advances when those ACKs arrive.

Launch arguments:

```bash
# Change the initial delay before command 1 (seconds)
ros2 launch leroi_bringup integration_test.launch.py startup_delay_sec:=8.0

# Run without a robot: the driver fakes the robot ACKs itself
ros2 launch leroi_bringup integration_test.launch.py simulate_robot_ack:=true
```

To edit the command scenario, change the `TEST_SEQUENCE` list at the top of
`integration_test.launch.py` (action ids 0–22 are mapped in
`leroi_decision/decision_node.py`).

### Watch decision / robot topics live

```bash
# Approved commands the decision node forwards to the robot
ros2 topic echo /robot/command

# Decision node state (waiting_for_ack, pending command, blocks_collected, last ack/rejection)
ros2 topic echo /decision/status

# ACKs coming back from the robot (or the sim driver)
ros2 topic echo /robot/action_ack

# Commands being requested into the decision node
ros2 topic echo /decision/action_request

# Commands the decision node rejected, with the reason (BUSY_WAITING_FOR_ACK, REJECTED_NO_BLOCKS, ...)
ros2 topic echo /decision/rejected

# Append-only log of every command the decision node sent
ros2 topic echo /decision/command_log

# Sanity checks
ros2 topic list | grep -E 'decision|robot'
ros2 topic hz /decision/status
```
