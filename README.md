# Leroi AI — Jetson ROS 2 Workspace

ROS 2 (`colcon`) workspace for running the Leroi AI stack on NVIDIA Jetson.

This repo is structured as a standard ROS 2 workspace:

- `src/` — source packages
- `build/`, `install/`, `log/` — generated by `colcon` (safe to delete/rebuild)

Main build command (run from the repo root; source the install overlay after building):

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

## Project structure

Each ROS 2 package usually contains:

- one or more node files or node entrypoints
- any supporting Python/C++ code the node needs
- `package.xml` and build/setup metadata

Launch files live in the bringup package, which is used to start one or more nodes together.

## Packages

This workspace contains the following ROS 2 packages:

- `leroi_bringup` — launch package used to start one or more ROS 2 nodes together.
- `leroi_perception` — perception node package for camera input, preview streaming, and YOLO-based detections.
- `leroi_decision` — decision-making package that will consume perception outputs and choose actions.
- `leroi_policy` — policy package for higher-level behavior or control logic that guides decisions.
- `leroi_serial_messenger` — serial communication package for Jetson ↔ microcontroller messaging.
- `leroi_dashboard` — VexAI dashboard sync for robot pose, blocks, and camera stream.
- `leroi_telemetry` — telemetry package for publishing or exporting system status and runtime metrics.
- `leroi_interfaces` — interface package for shared custom messages and services.

Below is a short summary for each package followed by details.

### `leroi_bringup` (ament_python)

Bringup / launch package for the workspace. It contains launch files that start one or more nodes together and pass common parameters.

- Launch files: `perception.launch.py`, `robot.launch.py` (installed via `setup.py` data files)
- What they do: the provided launch files start the `perception_node` from `leroi_perception` and set a small set of default parameters (for example `publish_rate_hz` and `enable_fake_detections`). Edit or add launch files here to compose multiple nodes for your robot.
- Example:

```bash
ros2 launch leroi_bringup perception.launch.py
```

### `leroi_perception` (ament_python)

Full-featured perception package providing `PerceptionNode` (entrypoint `perception_node`). The node supports multiple camera sources (including OAK), an MJPEG preview stream, and an optional YOLO inference pipeline.

- Node entrypoint: `perception_node` (`ros2 run leroi_perception perception_node`) — registered in `setup.py` as `leroi_perception.perception_node:main`.
- Main features:
	- Camera source abstraction via `create_camera_source` (configured by `camera_type`, `camera_index`, `oak_mxid`, and resolution).
	- MJPEG preview streamer (`enable_preview_stream`, `preview_port`, `preview_jpeg_quality`) that serves a live preview (default host 0.0.0.0).
	- Optional YOLO detector wrapper (`YoloDetector`) with parameters to control model path, device, confidence, image size, and half precision.
	- Background camera reader thread plus timers for preview framing, status updates, and YOLO inference.
- Topics (per-camera):
	- `/perception/<camera_name>/status` (`std_msgs/String`) — JSON status packet including timestamps, counts, and runtime stats.
	- `/perception/<camera_name>/detections` (`std_msgs/String`) — JSON detection packet with fields such as `frame_id`, `image_width`, `image_height`, `detection_count`, and `detections` (each detection contains `class_name`, `class_id`, `confidence`, `x,y,z`, and `bbox_*` keys when available).
- Important node parameters (defaults taken from the node implementation):
	- Camera: `camera_name`=`oak_front`, `camera_type`=`oak`, `camera_index`=0, `camera_width`=640, `camera_height`=480, `camera_fps`=30, `oak_mxid`=""
	- Rates: `preview_rate_hz`=30.0, `status_rate_hz`=2.0, `yolo_rate_hz`=15.0
	- YOLO: `enable_yolo`=False, `yolo_model_path`="", `yolo_confidence`=0.35, `yolo_image_size`=320, `yolo_device`="cpu", `yolo_use_half`=False
	- Preview: `enable_preview_stream`=True, `preview_port`=8080, `preview_jpeg_quality`=70, `draw_detections`=True

### Decision command testing

`leroi_bringup/launch/integration_test.launch.py` drives the `decision_node` through a
fixed command sequence so you can verify the action handshake end to end. It brings up
the serial messenger, perception, the decision node, and a `decision_test_driver` that
sends commands one at a time, waiting for each ACK before sending the next:

1. `MOVE_CHASSIS_ONLY` (action_id 1) → first target point
2. `MOVE_CHASSIS_ONLY` (action_id 1) → second target point
3. `COLLECT_BLOCKS` (action_id 2) → several target points

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch leroi_bringup integration_test.launch.py
```

The driver waits 5 s after launch before sending the first command. By default it
expects the **real robot** (via `leroi_serial_messenger`) to return the ACKs on
`/robot/action_ack`; the sequence only advances when those ACKs arrive.

Launch arguments:

```bash
# Change the initial delay before command 1 (seconds)
ros2 launch leroi_bringup integration_test.launch.py startup_delay_sec:=8.0

# Run without a robot: the driver fakes the robot ACKs itself
ros2 launch leroi_bringup integration_test.launch.py simulate_robot_ack:=true
```

To edit the command scenario, change the `TEST_SEQUENCE` list at the top of
`integration_test.launch.py` (action ids 0–22 are mapped in
`leroi_decision/decision_node.py`).

### Gyro / heading reset (`RESET_GYRO`, action_id 24)

The IMU/heading lives on a separate **ESP32-C6 odom board** (its own USB-C serial
port, native USB CDC — baud is ignored). Its firmware scans incoming bytes for a
command letter: `R`/`r` = full reset (recalibrate bias + zero heading, ~1.2 s, board
must be still); `Z`/`z` = zero-heading-only (instant).

`RESET_GYRO` (action_id 24) couples that board reset to the robot so it happens
safely mid-routine:

1. Send action 24 like any other action (test driver, policy, or `ros2 topic pub`).
   It is allowed to **interrupt** an in-flight action (decision node treats it like
   `STOP`), so the robot can drop what it's doing.
2. The V5 stops, holds still, and sends its `ACK ... DONE` for command 24.
3. On that ACK, the **serial messenger writes the reset char to the odom board** over
   the board's own USB-C port (open → write → close; it never reads the board, so
   `printf 'R' > /dev/ttyACMx` still works manually).

So the Jetson never resets the gyro while the robot is moving — the V5's ACK is the
"I'm holding still" handshake that gates the write.

Trigger it manually (through the running decision → serial pipeline):

```bash
ros2 topic pub --once /decision/action_request std_msgs/String "data: '24'"
# or full form:
ros2 topic pub --once /decision/action_request std_msgs/String \
  "data: '{\"action_id\":24,\"action_name\":\"RESET_GYRO\"}'"
```

**Startup reset (no V5, no ACK):** set `gyro_reset_on_startup:=true` to fire one
reset straight to the board ~`gyro_startup_reset_delay_sec` after the node starts.
Use this when you've squared the robot up at heading 0 by hand and just want the
board zeroed before the run — `integration_test.launch.py` enables this by default.

Relevant `serial_messenger_node` parameters:
- `gyro_reset_on_ack` (default `true`) — enable the on-ACK coupling.
- `gyro_reset_on_startup` (default `false`) — fire one reset at node startup.
- `gyro_startup_reset_delay_sec` (default `2.0`) — wait before the startup reset.
- `gyro_reset_action_id` (default `24`).
- `gyro_board_port` (default `""` = auto-detect by the Espressif by-id string; ACM
  numbers are not stable, so prefer auto-detect). Set explicitly to override.
- `gyro_board_keywords` (default `"USB JTAG/serial debug unit,Espressif"`).
- `gyro_reset_char` (default `"R"`; use `"Z"` for zero-only).
- `gyro_reset_delay_sec` (default `0.0`) — optional settle wait after the ACK.

> **V5-side note:** keep the robot still for ~1.2 s *after* ACKing a full (`R`) reset
> so the recalibration completes cleanly. The `decision_node` won't issue the next
> action until something requests one, but if you auto-chain commands, leave a gap
> (or use `gyro_reset_char:="Z"` for an instant zero-only reset). The reset count is
> reported on `/serial_messenger/status` as `gyro_reset_count`.

### Policy: RL model **or** defined strategy (confirm/cancel → decision)

The `leroi_policy` package can drive the robot two ways, selected by the
`strategy_mode` parameter. Both produce the same `ActionProposal` and feed the
same pipeline — `game state → strategy.propose() → (operator confirm/cancel) →
/decision/action_request` — so the rest of the stack doesn't care which is active.

- **`strategy_mode:=rl`** — runs an exported RL model (ONNX): `build_observation()`
  → model → argmax → `action_id`. This is the learned policy.
- **`strategy_mode:=scripted`** — executes a fixed, repeatable game plan with **no
  learning**: a state machine that
  1. moves to a **scan** position near our parking zone and looks at the goals,
  2. **assesses** goal state from perception (our-color vs opponent-color blocks in
     the goal regions, and how full they are), then branches:
     - mostly **opponent** colors → **DESCORE**
     - mainly **our** colors → **collect** more, then **score mid/low**
     - neutral & ~empty → **collect** more, then **score long goal**
     - neutral & ~full → **DESCORE**
  3. returns to the scan position and repeats.

  Goal state is read from the configured **goal regions** (perception cm). Collect
  targets come from the **route planner** (`/perception/route_suggestion`), which
  already clusters, applies wall margins, skips goals, and respects a pickup zone;
  the strategy converts those cm points to inches and zone-clamps them.

Architecture (so both modes stay swappable):

- `leroi_policy/strategies/base.py` — `GameState`, `ActionProposal`, `Strategy` ABC.
- `leroi_policy/strategies/rl_strategy.py` — the ONNX model wrapper. **`build_observation()`
  now lives here** (this is the function you must align with your sim's obs space).
- `leroi_policy/strategies/scripted_strategy.py` — the defined game-plan state machine
  (scan → assess → branch → scan).
- `leroi_policy/strategies/actions.py` — shared action-id vocabulary.
- `leroi_policy/policy_node.py` — thin ROS driver: builds `GameState` (odom, mapped
  objects, route suggestion), calls the selected strategy, runs the confirm/cancel
  gate, publishes the request.

**Units:** perception is in **cm**, the V5/odom is in **inches**. The scripted
strategy converts collect/route points cm→inches (`perception_to_robot_scale`,
default 1/2.54). Author scan/fallback waypoints directly in inches.

**Left-half zone (24in robot):** to avoid impeding the 15in robot on the right, the
route planner only routes to blocks with `x ≤ pickup_x_max_cm` (default 182.88 cm =
72 in), and the strategy clamps any waypoint past `zone_x_max_in` (default 72 in,
+`zone_x_wander_in`).

`leroi_bringup/launch/integration_policy_test.launch.py` brings up serial messenger,
perception, the decision node, and `policy_node`, and gates every proposed action
behind an operator confirm/cancel so you can vet it before it commands the robot.

```bash
source /opt/ros/humble/setup.bash
source install/setup.bash

# RL model (default). Point at your sim's export:
ros2 launch leroi_bringup integration_policy_test.launch.py \
    strategy_mode:=rl \
    policy_model_path:=$HOME/leroiai-jetsonWorkspace/models/policy/policy.onnx

# Defined strategy (no model needed):
ros2 launch leroi_bringup integration_policy_test.launch.py \
    strategy_mode:=scripted alliance_color:=blue

# Route-planner test (dedicated launch): forward planner points to the V5 on confirm:
ros2 launch leroi_bringup route_planner_test.launch.py alliance_color:=blue
```

**Quick test — route planner → V5 (confirm/deny).** `route_planner_test.launch.py` is a
self-contained launch (serial + perception + route planner + decision + policy in
`route` mode) — a good candidate to run on startup later. It runs a minimal forwarder:
perception → route planner → it proposes the route as a `COLLECT_BLOCKS` action (points
converted cm→inches) and holds it for your approval. (The same is available on
`integration_policy_test.launch.py strategy_mode:=route`.)

```bash
# See the points it wants to send (inches), and the raw planner output (cm):
ros2 topic echo /policy/pending_action
ros2 topic echo /perception/route_suggestion

# Approve -> goes to decision -> /robot/command -> serial -> V5:
ros2 topic pub --once /policy/decision std_msgs/String "data: 'confirm'"
# Deny (nothing sent; it will re-propose the current route):
ros2 topic pub --once /policy/decision std_msgs/String "data: 'cancel'"
```

On confirm, the serial messenger (with `debug_log_tx` on in this launch) prints the
exact command sent to the V5 — `TX type=5 ... payload={"type":"ACTION","action_id":2,
"points":[...]}` — so you can verify the points on the wire. One command is sent per
confirm; it waits for the V5 ACK before offering the next route.

**Action-space safety.** Commands are validated against the defined action space
(`ACTION_NAMES`, ids 0–22 and 24) at two points so an undefined command can never reach
the serial messenger / V5: the `policy_node` refuses to propose or send an unknown
`action_id`, and the `decision_node` rejects unknown ids (`reject_unknown_action_ids`,
default true) with `UNKNOWN_ACTION_ID` on `/decision/rejected`.

The scripted strategy's waypoints/ids are parameters on `policy_node` (defaults are
placeholders to tune to the real field):
- `alliance_color` (`blue`/`red`) — selectable per match; also picks default
  score-long / score-mid-low / descore (wall-side) goal ids.
- `score_long_action_id`, `score_midlow_action_id`, `descore_action_id` — `0` = use
  the alliance default.
- `scan_point_blue_json` / `scan_point_red_json` — scan position per alliance, JSON
  array of `{x,y,heading}` in **inches** (near that alliance's parking zone).
- `collect_fallback_blue_json` / `collect_fallback_red_json` — collect waypoints
  (inches) used only if the route planner has no suggestion.
- `goal_regions_json` — list of `{name,x_min,x_max,y_min,y_max}` rectangles in
  field **cm** used to decide which blocks count as "in a goal". Empty → assess all
  detected blocks (rough proxy until calibrated).
- `goal_color_margin` (dominance threshold), `goal_empty_max`, `goal_full_min`
  (fullness thresholds, block counts).
- `max_collect_targets`, `use_route_planner_for_collect`, `zone_x_max_in`,
  `zone_x_wander_in`, `perception_to_robot_scale`.

Launch args: `strategy_mode`, `alliance_color`, `zone_x_max_in`, `pickup_x_max_cm`.
Watch the current plan/phase + last assessment on `/policy/status`.

Confirm or cancel the currently proposed action:

```bash
# See what the policy is proposing
ros2 topic echo /policy/pending_action

# Approve it
ros2 topic pub --once /policy/decision std_msgs/String "data: 'confirm'"

# Approve a point-based action (MOVE/COLLECT) and supply points inline (x,y,heading):
ros2 topic pub --once /policy/decision std_msgs/String "data: 'confirm 250,200,90 270,220,45'"

# Reject it (policy proposes again next tick)
ros2 topic pub --once /policy/decision std_msgs/String "data: 'cancel'"
```

Notes:
- **ONNX runs on CPU.** The policy is a small MLP at ~1 Hz, so CPU is plenty and it
  keeps the GPU free for perception's YOLO TensorRT engine. To use the GPU you must
  install NVIDIA's Jetson `onnxruntime-gpu` build, then set the `onnx_providers` param
  (e.g. `TensorrtExecutionProvider,CUDAExecutionProvider,CPUExecutionProvider`).
- onnxruntime install: `pip install --user "onnxruntime==1.17.0"` (newer PyPI wheels
  crash on this Tegra CPU).
- **`build_observation()` in `leroi_policy/strategies/rl_strategy.py` must match your
  sim's observation space** (feature order/normalization/dimension). The default layout
  is a placeholder; it zero-pads/truncates to the model's input size and logs a one-time
  warning on mismatch. (Only used by `strategy_mode:=rl`.)
- `models/policy/policy_dummy.onnx` is a random-weights stub (obs 65 → 23 actions) for
  validating the wiring before the real model exists. Launch with
  `policy_model_path:=$HOME/leroiai-jetsonWorkspace/models/policy/policy_dummy.onnx`.
- Auto-run mode (no confirmation) for live play: add `require_confirmation:=false`.
